# خط لولهٔ دارایی

بارگذاری و تبدیل مدل‌ها، تصاویر و صداها.

---

## فرمت‌های پشتیبانی‌شده

| نوع | فرمت | کتابخانه |
| --- | --- | --- |
| مش | OBJ (+MTL)، FBX | دست‌ساز / ufbx |
| تصویر | PNG، JPG | stb_image |
| صدا | WAV، MP3، OGG، FLAC | dr_libs + stb_vorbis |

- `.mtl` و `.blend` نوع مستقل نیستند؛ برای `.blend` مسیر File > Export > OBJ/FBX مستند شده (پارسر عمداً وجود ندارد).
- متریال (`MaterialData`): نام + رنگ پخش + مسیر تکسچر؛ «گذاشتن عکس روی جسم» = ساخت/به‌روزرسانی متریال.
- قرار دادن در صحنه: فایل‌های OBJ/FBX پوشهٔ `assets` با **فیت خودکار بزرگ‌ترین بُعد** وارد می‌شوند (مثل ایمپورت یونیتی).

## API

```cpp
kimia::assets::detectType(path)          // نوع با پسوند (بدون حساسیت به بزرگی)
kimia::assets::loadMesh / loadOBJAsset / loadFBXAsset
kimia::assets::loadImage / loadAudio     // std::optional + پیام خطا
kimia::assets::loadFBXSkinned(path, err) // مش پوست‌دار + اسکلت + کلیپ‌ها
```

- `MeshData`: `positions/normals/uvs` هم‌اندازه + `indices` مثلثی (مضرب ۳).
- `MeshAsset`: مش ترکیبی + `materials` + `subMeshes` (خالی = بدون متریال).
- `Image`: پیکسل‌های `u8` سطر-عمده (سطر ۰ = بالا).
- `AudioBuffer`: PCM میان‌گذاری‌شدهٔ `f32`؛ `encodeWAV()`؛ صداهای رویه‌ای `tone`/`thock`/`concat`.

## قراردادهای مش

- مثلث‌ها از بیرون **پادساعتگرد**؛ نرمال‌ها بیرون‌سو.
- OBJ: هر گوشهٔ face یک رأس؛ چهارضلعی → ۴ رأس/۶ ایندکس (مکعب استاندارد ۲۴v/۳۶i)؛ UV با قرارداد OBJ برگردانده می‌شود.
- FBX: محورها به راست‌دست Y-up، واحد به متر، نرمال‌های گم‌شده تولید و تاپل‌های یکسان ادغام می‌شوند.
- فرمت متنی مش KIMIA v1 (سرآیند `# KIMIA mesh v1`؛ بارگذاری مقاوم).

## ابزار خط فرمان

```bash
./build/bin/kimia_assets_cli model.fbx texture.png sound.mp3
```

گزارش متریال‌ها (نام/رنگ/تکسچر) + فایل‌های تبدیل‌شدهٔ کنار فایل اصلی (`.kimiamesh`، `.kimi.png/.kimi.jpg`، `.kimi.wav`).

## داده‌های تست

`Tests/assets/` — دارایی‌های کوچک با `kimia_asset_gen` تولید می‌شوند؛ فایل‌های مرجع (box.fbx، textured.fbx، spider.obj، sfx.ogg، tone.flac، …) از مخازن بالادستی رسمی کپی شده‌اند.

## پک‌های حجیم: بیرون مخزن، با manifest داخل مخزن (سیاست 0.30)

مخزن اصلی فقط asset **کوچک و عملکردی** نگه می‌دارد (امروز جمعاً زیر ۱ مگابایت:
`assets/` و `Tests/assets/`). دلیلش永久性 است: هر `git clone` — روی CI، روی
Termux، روی ماشین هر همکاری — کل *تاریخ* را می‌کشد، نه فقط نوک شاخه. یک گیگابایت
داخل Git یعنی هر کلون تا ابد یک گیگابایت سنگین‌تر؛ حتی اگر فردا فایل‌ها را پاک
کنی، در تاریخ می‌مانند. پس:

- **حجم زیاد بیرون می‌ماند:** یک مخزن جدا (مثلاً `KIMIA-ASSETS`) با Git LFS، یا
  یک آرشیو روی GitHub Releases. داخل این مخزن فقط یک *manifest* می‌آید: نام پک،
  نسخه، منبع دانلود، sha256 و فهرست فایل‌های موردنیاز — یعنی موتور می‌داند چه
  چیزی کم دارد و از کجا، بدون اینکه خودش حملش کند.
- **staging در sandbox بیرون مخزن است** (پوشهٔ uploadها). آنچه commit می‌شود فقط
  *گزیدهٔ کیوریت‌شده* است: مش‌های لوپلی، تکسچرهای ≤۲K، و صداهای لازم برای
  vertical slice — با سقف‌های جدول پایین.
- **بودجهٔ هر فایل برای گوشی/Termux:**

  | مورد | سقف |
  | --- | --- |
  | مش کاراکتر | ≤ ۵ هزار مثلث، یک متریال، تکسچر ≤ ۱۰۲۴ |
  | prop / دروازه / توپ | ≤ ۳ هزار مثلث؛ توپ ۶۳ مگابایتی بیرون می‌ماند، داخل بازی توپ ساده یا decimate‌شده |
  | تکسچر متریال (سنگ/آسفالت/آجر/کاشی) | ≤ ۲۰۴۸ دسکتاپ، ≤ ۱۰۲۴ موبایل |
  | صدا | OGG/MP3 استریو ≤ ۳ مگابایت per track |
  | FBX اسکلت‌دار | ریگ با نام bone لاتین؛ کلیپ‌ها همنام با حالت‌های گیت (`idle/walk/run/sprint/stop/kick/pass/tackle`) |

- **اسکریپت‌های Unity وارد بیلد موتور نمی‌شوند.** آن‌ها C# اند و اینجا کامپایل
  نمی‌شوند؛ کپی‌شان در شاخهٔ build یعنی کد مرده. جایشان یا مخزن جداست یا پوشهٔ
  `Reference/Unity/` به‌صورت *منبع مرجع*، و برای هر اسکریپت یک «نقشهٔ پورت»
  نوشته می‌شود: MonoBehaviour معادلِ موتوریش چیست (کلید پروفایل، قانون در
  `Rules.cpp`، ability در سیستم قدرت‌ها، منطق داده‌محور در Logic).

- **فونت فارسی:** در Workbench مرورگری رایگان است (مرورگر خودش شکل‌دهی RTL را
  می‌کند و CSS فونت را می‌گیرد). برای HUD *داخل* رندر، شکل‌دهی و راست‌به‌چپ
  هنوز پیاده‌سازی نشده — یک قابلیت صادقانه در فهرست فاز ۸، نه یک شکستگی پنهان.
