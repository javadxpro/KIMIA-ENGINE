# Scene و هویت موجودیت‌ها (فاز ۳)

این سند دو چیز را قطعی می‌کند که تا امروز ضمنی و پراکنده بودند: **هویت یک
موجودیت** (چه چیزی یک شیء را در طول زمان و در فایل مشخص می‌کند) و **قرارداد
فایل صحنه** (چه نسخه‌ای نوشته می‌شود و فایل قدیمی چطور خوانده می‌شود).

## ۱. دسته (handle)

```
using EntityHandle = u32;
inline constexpr EntityHandle kNullEntity = 0U;
```

* دسته‌ها **از ۱ شروع می‌شوند**؛ صفر یعنی «هیچ».
* یک دسته **هرگز دوباره صادر نمی‌شود**. `Scene::create` فقط `nextHandle_` را
  بالا می‌برد، و `destroy` آن را برنمی‌گرداند. پس اگر یک شیء حذف شود و بعد
  صد شیء دیگر ساخته شود، دستهٔ قدیمی هنوز به هیچ‌چیز اشاره نمی‌کند.
* نتیجهٔ مهم: **نسل (generation) لازم نیست**. الگوی کلاسیک «id + generation»
  برای این است که دستهٔ کهنه به شیء جدید اشاره نکند؛ این‌جا چون id هرگز تکرار
  نمی‌شود، دستهٔ کهنه از خودِ id قابل تشخیص است — `get()` تهی برمی‌گرداند و
  `alive()` غلط است. این تصمیم عمدی است، نه سهل‌انگاری: یک عدد ۶۴ بیتی با
  بسته‌بندی/نسل، هم فایل را بزرگ‌تر می‌کند و هم هر مصرف‌کننده را مجبور می‌کند
  دو فیلد را درست حمل کند.
* تکرار در پیمایش، **به ترتیب دسته** است (پایهٔ خروجی پایدار در
  `SceneIO`). دسته‌ها داخل `std::map` نگه داشته می‌شوند؛ `find` روی نمایهٔ نام
  کار می‌کند، نه پیمایش.

## ۲. نام و تکراری‌ها

نام‌ها **کلید کاری ویرایشگر و بازی‌ها** هستند (`scene.find("Ball")`)، پس
قواعدشان صریح می‌شود:

* **نام تکراری مجاز است.** حذف نمی‌شود و خطا هم نیست؛ فایل‌های قدیمی و
  ابزارهایی که با نام کار می‌کنند نباید بشکنند.
* `find(name)` همیشه **کم‌ترین دستهٔ زنده** با آن نام را برمی‌گرداند. این
  قاعده در `Scene::create` (اولی برندهٔ نمایه است)، در `reindex()` و در
  `rename()` یکسان رعایت می‌شود. نتیجه: پاسخ `find` با ترتیب فایل و با
  ترتیب ساخت یکی است و بین اجراها تغییر نمی‌کند.
* نام خالی نمایه نمی‌شود: «بی‌نام» یعنی با نام پیدا نمی‌شود.
* `Scene::uniqueName(wanted)` نام آزادِ سبک ویرایشگر را می‌سازد
  («Block»، «Block_2»، «Block_3»، …). این تابع حالا در خود `Scene` است و
  `Library::stamp` و ساخت بلوک‌ها از آن استفاده می‌کنند تا دو پیاده‌سازی
  متفاوت از یک قاعده نداشته باشیم.

### نمایهٔ نام

`find` قبلاً **پیمایش کل صحنه** بود، و در درخت ۲۴۱ محل صدا زدن دارد؛ چند
تای‌شان داخل حلقه‌اند (`nextNumber`, بازسازی فیزیک، جست‌وجوی صدا). حالا یک
`std::unordered_map<std::string, EntityHandle>` کنار `entities_` نگه داشته
می‌شود:

* `create` و `restore` و `rename` و `destroy` آن را به‌روز می‌کنند؛
* `find` اول نمایه را می‌پرسد، و اگر پاسخ نبود **یا نامِ ثبت‌شده دیگر با
  موجودیت نخواند**، یک بار `reindex()` می‌کند و دوباره می‌پرسد.

آن «نخواند» عمدی است: نام یک فیلد عمومی در `EntityData` است و کد زیادی
(`Studio`, `WorldBuilder`, ابزارها) با نوشتن مستقیم `entity->name` تغییرش
می‌دهد. نمایه‌ای که با چنین تغییری از واقعیت جدا شود، بدترین حالت است
(جست‌وجو دروغ می‌گوید). با تأییدِ نام در هر پاسخ، جدایی **قابل تشخیص** است و
خودش را تعمیر می‌کند؛ هزینه‌اش فقط یک بازسازی پس از یک تغییر مستقیم است،
نه در هر فریم. تعداد بازسازی‌ها در `nameIndexRebuilds()` شمرده می‌شود تا
«نمایه کار می‌کند» یک اندازه‌گیری باشد، نه ادعا.

## ۳. قرارداد فایل (`SceneIO`)

فرمت متنِ v1 دست‌نخورده می‌ماند. کارهای این فاز:

**نسخه.** `SceneIO::kVersion = 3`. هر ویژگی فرمت نسخهٔ خودش را دارد
(`SceneIO::kIdVersion = 2`، `SceneIO::kMotorVersion = 3`) و نویسنده
**قدیمی‌ترین نسخه‌ای** را می‌نویسد که صحنه را بیان می‌کند:

| صحنه | سرصفحه | id ها |
| --- | --- | --- |
| دسته‌ها ۱..N پشت‌سرهم، بدون موتور (هر صحنهٔ موجود) | `# KIMIA scene v1` | نوشته نمی‌شوند |
| دسته‌های غیرپشت‌سرهم، بدون موتور | `# KIMIA scene v2` | `id <n>` در هر خط |
| هر صحنه‌ای با موتور کاراکتر (v3 = `motor`) | `# KIMIA scene v3` | فقط اگر دسته‌ها ۱..N نباشند |

«قدیمی‌ترین نسخه‌ای که صحنه را بیان می‌کند» یعنی نسخه از **ویژگی‌های
استفاده‌شده** می‌آید، نه از نسخهٔ بیلد: یک صحنهٔ v3 با دسته‌های ۱..N هیچ `id`
نمی‌نویسد. (این را یک تست گرفت: مشتق‌کردن `withIds` از شمارهٔ نسخه، هر فایل
v3 را بی‌دلیل صاحب `id` می‌کرد.)

جدول نسخه‌ها:
`v1` خطوط موجودیت · `v2` = `id <n>` · `v3` = `motor <speed> <accel> <air>
<jump> <turn>` (سند `Documentation/CharacterMotor.md`).

پس هر جهان امروزی **بایت‌به‌بایت** مثل قبل ذخیره می‌شود (تست‌های موجود
`sceneio_roundtrip_byte_identical` این را نگه می‌دارند) و فقط صحنه‌ای که
واقعاً به شناسه نیاز دارد v2 می‌شود.

**خواننده.** v1، v2، v3 و فایل بی‌سرصفحه (همان v1) خوانده می‌شود؛ `id` های
v2 با `Scene::restore` بازیابی می‌شوند و شمارندهٔ دسته بالاتر از بزرگ‌ترین id
دیده‌شده می‌رود. فایل با نسخهٔ **جدیدتر از این موتور** خطا می‌دهد
(`scene file version 4 is newer than this engine understands (3)`) و شمارهٔ
نسخهٔ همین بیلد را در پیام می‌آورد، چون در آن حالت «تحمل» یعنی سکوت دربارهٔ
داده‌ای که نمی‌فهمیم.

**گزارش.** `SceneIO::LoadReport` می‌گوید بارگذاری چه چیزی دید:
`version` (نسخهٔ فایل)، `restoredIds`/`assignedIds`، `ignoredKeywords`
(کلیدواژه‌های ناشناخته، مرتب و یکتا) و `warnings` با **شمارهٔ خط**. دو مورد
آخری برای فاز ۱۰ (اعتبارسنجی فایل خراب) همان چیزی است که باید نمایش داده شود.

**`migrated` یعنی «مجبور شدیم چیزی بسازیم»**، نه «فایل از kVersion قدیمی‌تر
بود». فایل v1 که id ندارد اینجا شماره می‌گیرد و فایل با id تکراری یک id
تعمیری می‌گیرد؛ در هر دو حالت `migrated` روشن است. فایل v2 در موتور v3 هیچ
مهاجرتی نیست: هر ویژگی‌ای که به کار می‌برد سر جای خودش خوانده می‌شود و
بازنویسی‌اش فقط یک فایل دقیق را بی‌دلیل دست‌کاری می‌کند. با فرمتی که هر
ویژگی نسخهٔ خودش را دارد، «قدیمی‌تر از نسخهٔ فعلی» دیگر سؤال مفیدی نیست.

**مهاجرت.** تبدیل v1 به مدل فعلی **بی‌اتلاف و بی‌مرحله** است: همهٔ فیلدهای
v1 همان‌جا هستند و id ها به ترتیب خطوط ساخته می‌شوند، یعنی دقیقاً همان
دسته‌هایی که v1 هم داشت. پس «مهاجرت» در این فاز یک بازنویسی نیست؛ گزارش
می‌گوید فایل از چه نسخه‌ای آمده و نتیجه در حافظه نسخهٔ فعلی است.

**اعتبارسنجی عدد.** `parseF64` حالا `nan`/`inf` را رد می‌کند. `std::stod`
آن‌ها را می‌پذیرد و یک موقعیت NaN می‌تواند کل فیزیک را آلوده کند؛ خطی که
عدد نامعتبر دارد مثل قبل کامل رد می‌شود، ولی این بار **با هشدار**.

## ۴. وضعیت کامپوننت‌ها (فاز ۳)

| کامپوننت | وضعیت |
| --- | --- |
| `Transform`، `MeshKind`/`meshFile`، رنگ/نما | از قبل |
| `BodyComponent` (فیزیک)، `AnimationComponent`، `SoundComponent`، `tags` | از قبل |
| `DialogueComponent` (`say`) | سری اول همین فاز: ذخیره + API ویرایشگر |
| `CameraTargetComponent` (`camtarget`) | سری اول همین فاز |
| `CharacterMotorComponent` (`motor`, v3) | همین سری: ذخیره + سیم‌کشی واقعی به حرکت بازیکن |
| `AbilityComponent`، `ReplayMarkerComponent` | هنوز نیست — فاز ۶/۷. نشانهٔ ریپلی و رول توانایی بدون خودِ ریپلی/رول، هدرِ بی‌مصرف است |

## ۵. چه چیزی هنوز نیست

  هم‌زمان می‌آید تا دو بار دست نزنیم.
